Rekommenderade testfall för deltagarorganisationer
Denna sida beskriver rekommenderade testfall för deltagarorganisationer som vill genomföra egna verifieringstester av sitt meddelandesystem i SDK QA-miljö.
Om testfallen
Syftet med dessa testfall är att ge deltagarorganisationer möjlighet att självständigt verifiera sin anslutning till SDK QA-miljö.
Testerna är rekommenderade och kompletterar de obligatoriska testfall som genomförs inför federationsgodkännande.
Testfallen bygger på de funktionella tester som leverantörer av meddelandesystem genomför inför godkännande inom SDK. De kan användas för att verifiera installation och konfiguration av meddelandesystemet, genomföra egna kontroller efter uppgraderingar eller som stöd vid felsökning.
Förutsättningar
Deltagarorganisationens AP-operatör ska vara ansluten till SDK QA-miljö.
Deltagarorganisationen ska vara konfigurerad som deltagare i SMP i SDK QA-miljö.
Deltagarorganisationen ska ha skickat in SDK-anslutningsblankett.
Deltagarorganisationen ska ha en användare med rollen användaradministratör, som tilldelar rollerna organisationsadministratör samt adressadministratör.
Deltagarorganisationen ska ha registrerat funktionsadresser i SDK adressbok.
Deltagarorganisationens användaradministratör ska ha tilldelat rollen testklientanvändare.

SDK testklient
SDK testklient erbjuds till deltagarorganisationer och leverantörer som utvecklar SDK-anpassade lösningar. Information om SDK testklienten och hur en deltagarorganisation/leverantör får tillgång till den finns på sidan SDK testklient.
Genomförande av tester
Verifieringstester genomförs av deltagarorganisationen för att verifiera dess anslutning till SDK QA-miljön. Testfallen verifierar endast grundläggande funktionalitet.
Observera att testresultaten i SDK testklient sparas i sex månader. Under denna period är era testresultat tillgängliga för granskning inför godkännandeprocessen. Dröjer det mer än sex månader mellan testets genomförande och ansökan om federationsgodkännande behöver berörda tester göras om på nytt.
Deltagarorganisationen kan kontakta sin leverantör för meddelandesystem eller federationsägaren om det finns behov för vidare felsökning som rör meddelande- eller verksamhetslager (anslutande system), t.ex. om meddelanden eller meddelandekvittenser som förväntas komma fram till SDK testklient inte visas i användargränssnittet för SDK testklient.
Meddelandesystem, meddelandetjänst och meddelandeklient
I testfallen används begreppen meddelandesystem, meddelandetjänst och meddelandeklient för att beskriva vilka delar av deltagarorganisationens lösning som verifieras. Nedan förklaras begreppen.
Meddelandesystem
Den samlade lösning som deltagarorganisationen använder för att skicka, ta emot och hantera SDK-meddelanden. Ett meddelandesystem består normalt av en meddelandetjänst och en meddelandeklient.
Meddelandetjänst
Den tekniska komponenten i meddelandesystemet som ansvarar för att skicka, ta emot, validera, signera och kryptera SDK-meddelanden samt hantera meddelandekvittenser.
Meddelandeklient
Det användargränssnitt eller verksamhetssystem i meddelandesystemet där användaren läser, skapar och hanterar SDK-meddelanden.
Centrala begrepp i testfallen
I testfallen används ett antal tekniska begrepp som kan vara bra att känna till. Begreppen förklaras översiktligt nedan för att underlätta genomförandet av testerna.
AS4
AS4 är det kommunikationsprotokoll som används av accesspunkter inom SDK för att skicka och ta emot meddelanden mellan organisationer.
Protokollet innehåller funktioner för bland annat kryptering, signering och kvittenshantering som bidrar till en säker och tillförlitlig kommunikation.
När en användare skickar ett meddelande från sin meddelandeklient överlämnas meddelandet till organisationens meddelandetjänst. Meddelandet skickas därefter via organisationens accesspunkt till mottagarens accesspunkt med hjälp av AS4.
AS4 används bland annat för att:
skicka meddelanden mellan organisationer
skydda meddelandets innehåll genom kryptering under överföringen
verifiera avsändaren genom digital signering
säkerställa att meddelandet levereras till rätt mottagare
utbyta tekniska kvittenser mellan accesspunkter
O2O-certifikat (Organisation-to-Organisation-certifikat)
Ett O2O-certifikat används för att identifiera organisationer och skydda kommunikationen mellan deltagare i SDK. Certifikatet används bland annat för kryptering och signering av meddelanden så att endast avsedd mottagare kan läsa innehållet och så att mottagaren kan verifiera vem som skickat meddelandet.
Om ett O2O-certifikat är ogiltigt, har gått ut eller inte kan verifieras kan meddelanden inte skickas eller tas emot på ett korrekt sätt.
AS4-certifikat
Ett AS4-certifikat används av accesspunkter inom SDK för att etablera säkra anslutningar och skydda kommunikationen mellan organisationer. Certifikatet används för att identifiera accesspunkter och säkerställa att information skickas till rätt mottagare på ett säkert sätt.
Om ett AS4-certifikat är ogiltigt eller har gått ut kan kommunikationen mellan accesspunkter inte genomföras. Detta kan leda till att meddelanden inte kan skickas eller tas emot.
TLS-certifikat
Ett TLS-certifikat används för att skydda anslutningen mellan två system och säkerställa att kommunikationen sker på ett säkert sätt.
Om ett TLS-certifikat är ogiltigt eller har gått ut kan en säker anslutning inte upprättas, vilket kan leda till att meddelanden inte kan skickas eller tas emot.
Certifikatutfärdare (CA)
En certifikatutfärdare (Certificate Authority, CA) är en betrodd part som utfärdar och signerar certifikat. Om ett certifikat har utfärdats av en certifikatutfärdare som inte är betrodd kan en säker anslutning inte upprättas.
Signering
Signering innebär att ett meddelande förses med en digital signatur som gör det möjligt att verifiera vem som skickat meddelandet samt att innehållet inte har förändrats efter att det skickades.
Kryptering
Kryptering används för att skydda innehållet i ett meddelande så att endast avsedd mottagare kan läsa informationen.
Kryptering är en viktig del av säkerheten i SDK och används vid överföring av meddelanden mellan organisationer.
XHE
XHE är den del av ett SDK-meddelandes kuvert som innehåller teknisk information om meddelandet.
XHE kan liknas vid informationen på ett kuvert. Medan själva SDK-meddelandet innehåller den information som ska skickas mellan organisationerna, innehåller XHE de uppgifter som meddelandesystemen behöver för att kunna identifiera, dirigera och behandla meddelandet korrekt.
XHE innehåller bland annat information om:
avsändare
mottagare
meddelandetyp
referenser till andra meddelanden
annan teknisk metadata som behövs för kommunikationen
XHE innehåller även information som används vid signering och kryptering av SDK-meddelanden.
I vissa testfall används meddelanden där information i XHE medvetet är felaktig eller ofullständig. Syftet är att verifiera att meddelandesystemet upptäcker och hanterar sådana fel på ett korrekt sätt.
Meddelandekvittens
En meddelandekvittens är ett automatiskt svar från mottagande meddelandetjänst som visar om ett mottaget meddelande har accepterats eller avvisats.
Meddelandekvittenser används för att bekräfta att ett meddelande har behandlats och förekommer i flera av testfallen på denna sida.
ACCEPTED
ACCEPTED är en status i en meddelandekvittens som visar att mottagande meddelandetjänst har tagit emot och accepterat meddelandet.
REJECTED
REJECTED är en status i en meddelandekvittens som visar att mottagande meddelandetjänst har tagit emot men avvisat meddelandet.
En meddelandekvittens med status REJECTED innehåller normalt information om varför meddelandet avvisades.
Timeout
Timeout innebär att ett förväntat svar eller en förväntad meddelandekvittens inte tas emot inom angiven tid.
I vissa testfall används timeout-scenarier för att verifiera att meddelandesystemet hanterar uteblivna svar på ett korrekt sätt.
Integrationstester
Integrationstester används för att verifiera att deltagarorganisationens meddelandesystem kan kommunicera med andra system inom SDK.
Testerna fokuserar på de vanligaste meddelandeflödena och används för att säkerställa att meddelanden kan skickas, tas emot och hanteras korrekt mellan olika organisationer. De verifierar även att meddelandekvittenser kan tas emot och behandlas som förväntat.
Genom att genomföra integrationstesterna kan deltagarorganisationen verifiera att meddelandesystemet fungerar korrekt tillsammans med andra aktörer i SDK.
Testfall för meddelandetjänst
Meddelandetjänsten ansvarar för att skicka, ta emot, validera, signera och kryptera SDK-meddelanden samt hantera meddelandekvittenser.
Följande integrationstester används för att verifiera att deltagarorganisationens meddelandetjänst fungerar korrekt tillsammans med andra aktörer i SDK. Testerna fokuserar på att meddelanden och meddelandekvittenser kan skickas, tas emot och hanteras korrekt i kommunikationen med SDK testklient.
TF 2.0.1 SDK testklient skickar meddelande till deltagarens meddelandesystem
Syfte
Verifiera att deltagarorganisationens meddelandetjänst kan ta emot ett inkommande SDK-meddelande, generera en meddelandekvittens och vidarebefordra meddelandet till meddelandeklienten.
Teststeg
Skicka ett meddelande från SDK testklient till en av deltagarorganisationens funktionsadresser som är registrerad i SDK adressbok.
Kontrollera att en meddelandekvittens skickas tillbaka till SDK testklient. Detta innebär att mottagande deltagarorganisations egen meddelandetjänst validerar meddelandet korrekt och genererar automatiskt en meddelandekvittens.
Kontrollera att meddelandet levereras till den egna meddelandeklienten.
Kontrollera att innehållet i det mottagna meddelandet överensstämmer med vad som angivits i SDK testklient.
Kontrollera att SDK testklient har tagit emot en meddelandekvittens.
Förväntat resultat
Meddelandet tas emot av deltagarorganisationens meddelandetjänst.
Meddelandet vidarebefordras till meddelandeklienten.
Meddelandeinnehållet är korrekt.
En meddelandekvittens genereras och skickas tillbaka till SDK testklient.
Kommentar
Testfallet är automatiserat i SDK testklient och finns i testfallslistan i menyn ”Nytt anslutningstest” med namnet ”TF 2.0.1 Normalt meddelande (inga bilagor)”.
